# T1.6 Self-Loop 控制器：执行 → 验证 → 定位 → 修正

日期：2026-10-30
状态：已完成

## 1. 它解决什么问题

工作流里的 `loop` 只回答"最多跑几轮"，不回答"这一轮为什么还要跑、该换什么修正动作、什么时候该停"。Self-Loop 控制器把循环从"固定次数重试"变成**有依据的收敛过程**：

- 每轮验证后判断是否继续；
- 不达标时从三种动作里选一个：重写输出、换 Agent、补检索；
- 把判断依据、动作、分数变化、预算消耗写进循环记录，能在监控台直接展示；
- 只做修正，不自动改写工作流 DSL，避免"运行中改流程"的高风险。

## 2. 收敛条件（按优先级）

| 顺序 | 条件 | 记录值 |
|---|---|---|
| 1 | 分数 ≥ 验证阈值 | `passed` |
| 2 | 达到 `maxIterations` | `max_iterations` |
| 3 | 连续 N 轮没有超过最低增益 | `no_improvement` |
| 4 | 超过时间预算 | `budget_time` |
| 5 | 超过 token 预算 | `budget_tokens` |
| 6 | `while` 条件不再满足 | `while_false` |

- 阈值取自循环体内第一个 `verify` 节点的 `threshold`，缺省 0.8。
- 最低增益默认 0.01，即分数提升不超过 0.01 视为"没提升"。
- 初始验证已达标时直接跳过循环，不为了用掉轮次而重写合格产物。
- 首轮仍必跑，保持与旧 DSL 语义兼容。

## 3. 三种修正动作

| 动作 | 触发依据 | 执行方式 |
|---|---|---|
| `rewrite` 重写输出 | 默认；有具体验证问题时围绕问题重写 | 保留当前 Agent，在修正步骤输入注入 `selfLoop` 指令 |
| `swap_agent` 换 Agent | 至少一轮无提升，且调度器能找到能力匹配度 ≥ 0.5 的替代 Agent | 运行时覆盖该步骤的 `agent`，不修改 DSL；新 Agent 重新生成 |
| `retrieve` 补检索 | 问题文本命中"证据/引用/来源/检索/知识库/citation/evidence"等 | 生成 `retrievalQuery` 注入修正输入，由 Agent 或后续工具节点补材料 |

换 Agent 直接复用 T1.5 调度器：把当前 Agent 的能力标签作为任务需求，把其他启用 Agent 作为允许集合，取评分最高的候选。这样"换谁、为什么换"与调度日志使用同一套解释。

## 4. DSL 新增字段

`loop` 节点新增两个可选字段，画布抽屉会自动渲染：

```json
{
  "id": "revise-loop",
  "kind": "loop",
  "maxIterations": 2,
  "while": "${verify-loop.score} < 0.85",
  "patience": 2,
  "budget": { "maxDurationMs": 120000, "maxTokens": 0 }
}
```

- `patience`：连续无提升轮次上限，1–10，默认 2。
- `budget.maxDurationMs`：单次循环时间预算，0 表示不限，默认 120000。
- `budget.maxTokens`：单次循环 token 预算，0 表示不限，默认 0（关闭）。
- token 当前按输入输出序列化字符数 ÷ 2 估算，精确计量留给 T1.8 指标采集。

环境变量可提供全局默认值：`PLATFORM_LOOP_PATIENCE`、`PLATFORM_LOOP_MIN_GAIN`、`PLATFORM_LOOP_MAX_DURATION_MS`、`PLATFORM_LOOP_MAX_TOKENS`。

## 4.1 循环作用域 `${loop.*}`

循环体节点可以直接引用"进入本轮前"的循环状态，让修正基于上一轮产物而不是最初输入：

| 引用 | 含义 | 首轮取值 |
|---|---|---|
| `${loop.artifact}` | 进入本轮前的最新产物 | 循环外最近一个非验证节点的输出 |
| `${loop.issues}` | 上一轮验证问题 | 初始验证的问题清单 |
| `${loop.score}` | 上一轮验证分 | 初始验证分 |
| `${loop.iteration}` | 已完成的轮次 | 0 |
| `${loop.retrievalQuery}` | 控制器给出的补检索词 | 空 |

```json
{
  "id": "revise",
  "kind": "agent",
  "agent": "lesson-plan-agent",
  "inputs": {
    "draft": "${loop.artifact}",
    "issues": "${loop.issues}",
    "citations": "${search.citations}"
  }
}
```

- 只能在 `loop` 节点体内使用；写在循环外会报 `loop-ref-outside-loop`，写错键名会报 `unknown-loop-ref`。
- 配合循环体内的 `knowledge.search` 节点，`retrieve` 动作从"只注入检索词"变成真正的补充检索：

```json
{ "id": "search", "kind": "tool", "tool": "knowledge.search",
  "args": { "query": "${input.topic} ${loop.retrievalQuery}", "topK": 5 } }
```

## 4.2 最优产物保留

每轮结束保存一次作用域快照（产物、验证分、问题、输出表）。循环结束后：

- 把运行状态恢复到验证分最高的那一轮，下游 `${revise.output}`、`${verify-loop.score}` 拿到的是最优轮的值；
- 最优轮是初始产物（`bestIteration = 0`）时，用快照产物补位循环体节点的输出，避免下游引用缺失；
- 循环记录末尾写明保留结果，例如"保留第 1 轮产物，丢弃第 2 轮"；
- 被丢弃轮次的验证记录与步骤 trace 仍保留在库里，便于复盘。

## 5. 执行器如何接入

每轮循环体执行前，执行器把控制器上一步的决策写进 Agent 步骤输入：

```json
"selfLoop": {
  "iteration": 1,
  "action": "rewrite",
  "actionLabel": "重写输出",
  "targetScore": 0.85,
  "previousScore": 0.62,
  "issues": ["互动覆盖不足，沉默学生未参与"],
  "reason": "首轮修正：根据初始验证问题重写输出。",
  "budget": { "maxDurationMs": 120000, "maxTokens": 0 },
  "agentId": "lesson-plan-agent"
}
```

换 Agent 时额外带 `previousAgentId` / `agentId`，并通过运行时覆盖让该步骤实际调用新 Agent。

每轮结束写 `platform_loop_iterations`：

```
action: rewrite | swap_agent | retrieve
changes:
  得分 0.62 → 0.74（+0.12）
  验证问题：……
  下一轮动作：重写输出 —— 围绕验证问题重写输出。
  预算：1ms / 574 tokens
```

停止轮额外写入：

```
停止原因：达到验证阈值 —— 得分 0.86 ≥ 阈值 0.85，停止迭代。
```

运行输出新增 `tokensUsed` 与 `selfLoop` 汇总：

```json
"selfLoop": [{
  "loopNodeId": "revise-loop",
  "iterations": 2,
  "threshold": 0.85,
  "initialScore": 0.62,
  "finalScore": 0.86,
  "bestScore": 0.86,
  "bestIteration": 2,
  "stopReason": "passed",
  "tokensUsed": 1123,
  "elapsedMs": 3
}]
```

## 6. 接口

- `GET /api/platform/self-loop`：返回契约、三种动作、六种停止原因与默认策略。
- `GET /api/platform/health`：`selfLoop` 字段返回当前生效策略。
- 循环明细仍通过 `GET /api/platform/runs/:id/trace` 的 `loopIterations` 返回。

## 7. 实测

主链路（隔离服务 8899，classroom-v1）：

```
得分 0.62 → 0.74（+0.12）  下一轮动作：补检索
得分 0.74 → 0.86（+0.12）  停止原因：达到验证阈值（0.86 ≥ 0.85）
循环 2 轮，stopReason=passed，循环内约 1123 tokens
修正步骤输入带 selfLoop.action、targetScore=0.85、上一轮问题清单
```

> T1.7 三层验证器接入后，问题清单会带上 `证据支撑` 维度的未达标项，控制器据此把第二个动作判为 `retrieve` 而不是 `rewrite`；分数与停止原因不变。


换 Agent 探针（自定义验证器固定返回 0.7）：

```
第 1 轮 revise → weak-agent   动作 rewrite
第 2 轮 revise → weak-agent   动作 rewrite，决策：连续 1 轮无提升，换用资深教案 Agent
第 3 轮 revise → strong-agent 动作 swap_agent，决策：连续 2 轮无提升，停止
stopReason=no_improvement
```

达标跳过探针：初始分数 0.62 ≥ 阈值 0.3，循环体 0 次执行，`stopReason=passed`。

浏览器监控台：循环轮次显示 2 轮、动作标签、每轮分数变化、验证问题、下一轮动作、预算和停止原因；运行输出展示 `selfLoop` 汇总。控制台无报错。

测试：`npm run test:platform` 37 条全通过（控制器 6 条、执行器新增 3 条），`npx tsc -b`、服务端 typecheck、`npm run build` 均通过。T1.7 接入后平台测试扩到 45 条，仍全绿。

## 8. 边界

- 分数与问题来自验证器；stub 模式下由模拟打分器生成确定性数据，T1.7 已接入三层验证器与交叉验证。
- `retrieve` 由控制器生成检索词；是否真正补检索取决于循环体是否放置工具节点（基准工作流已用 `knowledge.search` + `${loop.retrievalQuery}` 落地）。
- 修正步骤必须显式绑定 `${loop.artifact}` / `${loop.issues}`；仍写死初稿引用时，多轮修正会退化为"每轮重写同一份初稿"。
- token 为估算值，不是模型返回的精确 usage。
- 不支持运行中自动改写工作流结构；换 Agent 只覆盖当前步骤的执行主体。
- 嵌套循环各自维护控制器状态，但共享同一个运行级状态机；`${loop.*}` 取最近一层循环的状态。
