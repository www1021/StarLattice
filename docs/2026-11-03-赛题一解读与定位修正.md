# 赛题一讲解解读、理解修正与参赛建议

> 来源：赛题一讲解会逐字稿与官方赛制说明 PPT（本地材料，不随仓库分发）
> - 日期：2026-11-03；初赛提交截止：2026-11-20

## 一句话结论

方向正确：赛题一做的就是 LobeHub / DeepSeek Harness 这类**通用 Agent harness**，用一个场景验证即可。但叙事要从“教育产品加了工作流”改成“**通用编排调度平台跑了教育场景**”，并把 Self-Loop、调度、验证做成可量化、可当场演示的证据。

---

## 一、讲解重点

### 1. 赛题一是基础设施，不是应用

- 官方 PPT 原文：“竞赛目标对标 LobeHub、DeepSeek Harness 等主流 Agent Harness 框架。”
- 老师原话：不需要解决实际工作问题；AI4S、化学、材料等具体产出**不作为最终评价依据**，评价的是调度中枢本身。
- 老师对“是不是做个 APP”的回答：可以理解成 APP，但它是**基础设施应用**；“不需要做小龙虾那么复杂，主要把自我循环、自我进化验证机制反映出来”。

### 2. 五个核心模块 + 一个灵魂

| 模块 | 要求 |
|---|---|
| Agent 定义与配置 | 多角色、技能、工具集、记忆；动态注册、发现、版本管理 |
| 工作流编排 | 顺序、并行、条件、循环、子工作流嵌套；可视化或代码化 |
| 任务调度与执行 | 按任务特征、Agent 负载、依赖、优先级动态分配 |
| 结果验证与监控 | 状态监控、中间结果、异常检测、自动/人工验证、交叉验证、置信度 |
| 反馈循环与优化 | 按验证结果调整 Prompt、工具选择或工作流路径 |

附加必展项：知识库/RAG、MCP 或 A2A、多 Agent 协作、至少一种 Self-Loop。

**灵魂是 Self-Loop**：老师全程重复最多，决赛明确要求突出“自我循环 + 错误修复 + Prompt 自适应优化”。

### 3. 差异化不在“能编排”

- PPT 明确说 Dify 等开源框架“内部并不具备良好的调度策略”；允许二开，但必须在调度策略、验证机制或自我循环上有明显自定义改进，禁止套默认示例。
- 可视化编辑器只是“可视化或代码化”二选一，是五模块之一，不是主战场。

### 4. 决赛加码项

- 模糊 Prompt → 意图理解 → Prompt 自适应优化 → 更符合预期的产出。
- 量化指标：任务成功率、响应延迟、并发能力，并与单 Agent / 串行基线对比。
- 自我循环要有“针对明确瓶颈”的设计和“收敛速度、准确率提升”的量化成效。

### 5. 评分结构

- 初赛：平台功能完整性 25 + 技术可靠性与可复现性 25 + AI 使用充分性与合理性 25 + 文档质量 25。
- 决赛：通用维度 40 + 专业维度 60。
- 专业维度细分：研究价值与创新性 10、架构设计与调度算法 10、自我循环与验证机制 10、结果验证与性能评估 10、工程化与落地 10、答辩 10。

### 6. 提交与评审提醒

- 初赛交：≥5000 字方案书 PDF、10–15 页 PPT、3–5 分钟视频、可运行代码仓库或在线演示地址。
- 老师特别提醒：往届有队伍答辩后关掉演示环境，导致评审无法二次验证；**在线 Demo 在评审期间必须保持可访问**。
- 本地运行不影响分数，但可复现性占 25 分，公网 Demo 是更稳的兜底。
- 命名：`赛题一+队伍名称+项目名称`；技术栈、开源协议、二开改动点必须写清楚。

## 二、原理解与修正

### 原理解（正确部分）

> 类似 LobeHub / DeepSeek Harness，做一个通用的编排平台，用一个基础问题验证，用教育行业落地。

这三层判断都成立：

1. 做通用 harness，不做垂直应用 —— 符合官方定位。
2. 选一个行业做验证 —— 老师明确说场景不限，具体行业产出不计分。
3. 教育可以作为验证场景 —— 官方鼓励结合真实行业需求。

### 需要修正的 3 点

| # | 原说法 | 修正 |
|---|---|---|
| 1 | 用“一个基础问题”验证 | 应是“一个**可验证的复杂任务**”。太基础会踩 PPT 红线：“单 Agent 简单调用或仅封装大模型 API 的作品不符合要求”。任务要能自然产生一次失败，才演得出验证与修正。 |
| 2 | “直接就变成工作流编排平台” | 说小了。编排只是五模块之一，且最不稀缺。评委看的是**调度决策是否智能、验证是否收敛、循环是否真的提升指标**。 |
| 3 | “通用”写在定位里就行 | “通用”必须被**演示出来**。如果产品名、首页、内置流程全是教育，会被归类为行业应用。教育应降级为“场景包/模板”，并至少有一个非教育场景证明通用性。 |

## 三、参赛建议（按性价比排序）

### 1. 先改定位，不改代码（本周完成）

- 对外统一名称：`XX 通用 Agent 编排调度平台`，StarLattice 作为“教育场景模板包”。
- README、PPT 第一页先讲平台能力，第二页才讲教育场景。
- 答辩开场话术：
  > 我们交付的不是一个教育应用，而是一个可被任何行业场景复用的 Agent 编排调度内核；教育是我们选择的第一个高保真验证场景。

### 2. 把教育验证设计成一条“能演戏”的链路

演示主线建议：

```
模糊需求
  → 意图澄清 / Prompt 改写
  → 任务分解
  → 知识库检索 + MCP 工具调用
  → 子工作流执行
  → 验证不通过（一个可复现、可解释的失败点）
  → Self-Loop 修正
  → 分数提升
  → 人工审批节点
  → 产出物
```

关键：**必须有一次真实的失败和一次真实的修正**。全程一次通过反而证明不了 Self-Loop。

### 3. 让调度“看得见”

- 运行 trace 展示：为什么选这个 Agent（任务特征、能力画像、负载、优先级、依赖）。
- 给一组对比数字：动态调度 vs 串行 / 单 Agent 的成功率、延迟。
- 这是决赛“架构设计与调度算法”10 分项，能力已有，主要差展示层。

### 4. 第二个场景必须可见

- 把已有的第二场景 DSL 放进“新建工作流”的模板库。
- 用 10 秒演示“同一个平台跑非教育任务”，这是“通用”的最强证据。
- 不需要做深，能跑通、能截图为证即可。

### 5. “模糊 Prompt → 自适应”做最小实现

- 澄清/改写 + 记录“原 Prompt vs 改写后” + 效果对比。
- 不新造子系统；11/10 冻结前能演即可。
- 这是决赛明确加码项，但优先级低于 Self-Loop 主链路。

### 6. 提交与合规清单

- [ ] 代码仓库转为公开（当前为私有，评审前必须处理）
- [ ] 在线 Demo 部署完成，评审期间不关闭
- [ ] README 含环境变量、启动命令、演示路径
- [ ] 技术栈、开源协议、二开改动点写入方案书
- [ ] `.env` 与历史提交无密钥
- [ ] 命名符合 `赛题一+队伍名称+项目名称`
- [ ] 方案书 8 章、≥5000 字；PPT 10–15 页；视频 3–5 分钟

### 7. 编辑层止损

- 11/10 功能冻结的决定保持。
- 拖拽体验对分数的贡献远小于自循环、验证、调度的证据。
- 创作层只做“新建/模板/绑 Agent 与工具/输出预览”，不再扩节点类型。

## 四、第二场景选型：经营数据分析

### 结论

选**经营数据分析报告（CSV → 指标 → 归因 → 报告）**，不做智能投研，不做代码审查。它是证明“通用性”性价比最高的选择：不新增引擎代码，同时换掉 Agent 团队、工具类别、验证规则和最终产物。

### 候选对比

| 候选 | 证明力 | 成本/风险 | 结论 |
|---|---|---|---|
| 经营数据分析（本地 CSV） | 强：数值复算、并行分支、工具选择 | 低：离线、确定性、可复现 | 推荐 |
| 智能投研 / 舆情简报 | 中：搜索 + 报告 | 高：实时 API、幻觉、评审时不可复现 | 不做 |
| 代码审查 / 自动修复 | 强：测试通过即验证 | 中高：GitHub token、沙箱、网络 | 备选 |
| 论文选题评审（已有 `topic-review-v1`） | 弱：仍属教育语境 | 零 | 保留为第三模板 |
| 法律 / 医疗 | 中 | 高：语料与合规负担 | 不做 |

### 场景设计

- **模板名**：`business-analysis-v1`「经营数据分析」。
- **输入**：内置一份销售 CSV + 一句模糊需求（“看看 Q3 为什么下滑，给三条建议”）。
- **Agent 团队**：规划 Agent（拆成趋势 / 区域 / 品类）→ 两个分析 Agent 并行 → 复核 Agent（复算 + 交叉核对）→ 报告 Agent。
- **工具**：新增本地 `data-analysis-mcp`（stdio，复用现有 MCP client），提供 `data.profile`、`data.groupby`、`data.trend`、`chart.render` 四个确定性工具。
- **知识库**：放“指标口径”规则（例如退款需从销售额扣除），同时证明知识库不是教育专用。
- **验证器**：报告里的每个数字必须与工具输出一致；每条结论必须引用一个计算指标；三个分析维度必须覆盖。
- **Self-Loop 触发点**：第一轮分析使用毛销售额、忽略退款口径，复核器发现数字对不上 → 回退重算 → 分数提升。这是真实的业务错误，不是硬造的 bug。
- **演示**：上传 CSV → 模糊问题 → 并行分析 → 验证失败（数字不一致）→ 自动修正 → 带图表的报告，30 秒内完成。紧接着切回教育模板，同一套 UI、同一套 trace。

### 为什么它比投研更适合初赛

教育场景的验证依赖量表，主观性难免；数据分析的验证可以复算。评委问“Self-Loop 真的有用吗”，可以直接给：第一轮 6 个数字错 4 个，循环后 6/6 一致，验证分从 X 提升到 Y（填实际值）。这比任何架构图都硬。

### 成本与排期

- 新增面积：1 个 workflow JSON、1 个约 150 行的 MCP server、1 份数据、2–3 条验证规则、1 个模板入口。
- 预计 1.5–2 天，11/5–11/7 完成，最晚 11/7 晚跑通。
- 止损：11/7 未跑通，立即退回已有的 `topic-review-v1` 作为第二模板，不占用 11/8–11/9 的 workflow-as-MCP 和 11/10 冻结。
- 数据：固定 CSV 或带生成脚本的合成数据，避免许可与联网问题。

### 边界

- 第一版不做 LLM 生成 Python 直接执行；用确定性工具，安全且可复现。
- 不做实时搜索，不接付费行情 API。
- 场景命名用“经营数据分析”，不要叫“金融投研”，避免被追问数据来源与合规。
- `topic-review-v1` 保留为第三模板，用于展示模板复用，不作为“跨行业”证据。

### 验收标准

- [ ] 模板库可见，可从空白或模板创建
- [ ] 一条命令启动，stub 模式零 token 可跑通
- [ ] 两个分析分支并行，trace 可见
- [ ] 第一轮验证必然失败且原因可解释
- [ ] Self-Loop 后数字一致率与验证分提升，记录前后值
- [ ] 图表与报告可下载或可截图
- [ ] 同一页面切回教育模板无异常

## 七、答辩三句话

1. **定位**：我们交付的不是一个教育应用，而是一个可被任何行业场景复用的 Agent 编排调度内核；教育是第一个高保真验证场景。
2. **自循环**：我们的 Self-Loop 不是概念，而是一次可复现的失败、一次自动修正和一组前后指标。
3. **调度**：调度不是随机分配，而是基于任务特征、Agent 能力画像、负载与依赖的动态决策，且决策过程在 trace 里可审计。
