### 阶段 1：平台内核（11/2 周一 – 11/8 周日）

这一周只做内核，不碰教育功能细节。每天一个模块，做不完就砍功能不砍接口。

#### [x] T1.1 数据模型与迁移
- 建 3.2 节 8 张表，写在 `server/platform/runtime/stateStore.ts` 初始化。
- **建议**：SQLite 用现有 `better-sqlite3`，不要引 ORM；表结构先宽后窄，别为范式纠结。
- 验收：重启服务表自动创建，`/api/platform/health` 返回表数量。
- 完成记录：`GET /api/platform/health` 返回 `tableCount: 8`；数据库默认 `data/platform.db`（可用 `PLATFORM_DB_PATH` 覆盖）。

#### [x] T1.2 工作流 DSL + 编译器
- 节点类型先定 6 种：`agent`、`tool`、`parallel`、`condition`、`loop`、`verify`。
- DSL 用 JSON（YAML 解析要额外依赖，先用 JSON）。
- 编译器负责：必填校验、拓扑排序、环检测、子流程展开、变量引用校验。
- **建议**：DSL 先服务主链路，不要设计成"什么都能表达"。表达力过剩 = 做不完。
- 验收：手写一份 `classroom-v1.json` 能编译通过；故意写环能报错。
- 完成记录：`server/platform/workflow/classroom-v1.json` 编译通过，`npm run test:platform` 覆盖环/重复 id/未知引用/条件表达式；验收详见 `docs/2026-10-30-平台内核T1.1-T1.2.md`。

#### [x] T1.3 Agent / Tool Registry
- Agent 字段：id、name、version、role、prompt、tools、model、capabilities（能力标签 + 权重）、memory。
- Tool 字段：id、name、type（builtin/mcp/http）、schema、endpoint。
- **建议**：把现有 5 类学生 Agent、观察员、教研/专家 Agent 直接注册进来，prompt 从 `studentAgentFactory.ts` 和 `classroomObserverAgent.ts` 抽出来。
- 验收：注册中心接口能列出 ≥8 个 Agent、≥5 个工具。
- 完成记录：新增 `server/platform/registry/agents.ts`（11 个 Agent）与 `registry/tools.ts`（7 个工具，builtin/mcp/http 各覆盖），启动时 `INSERT OR IGNORE` 注册，不覆盖手工修改；`PlatformStateStore` 增加 `seed/list/get/save` 两类实体，更新省略字段时保留原值、版本 +1；新增 `GET/POST /api/platform/agents`、`GET/POST /api/platform/tools` 与 `/health.registry` 汇总。实测 11 Agent / 7 工具，新增 Agent/工具不改代码，重启后种子幂等且自定义记录保留。详见 `docs/2026-10-30-注册中心T1.3.md`。

#### [x] T1.4 运行时执行器
- 状态机：`queued → running → verifying → revising → succeeded / failed / rolled_back`。
- 必须支持：并发节点、超时、重试（指数退避）、失败回滚、每步快照。
- **建议**：先做"能跑 + 有 trace"，再做回滚。回滚用"快照 + 反向执行"太复杂，改成"恢复到上一步快照"即可。
- 验收：主链路能跑完；人为让某节点抛错，能重试 2 次后标记失败并保留 trace。
- 完成记录：执行器新增 `queued/running/verifying/revising` 状态写入；单步超时（默认 30s）、指数退避重试（默认 3 次，200ms 起、上限 2s）、成功步骤快照、失败回滚（`rolled_back` + `rolledBackTo`）、并行分支 `allSettled` 收敛；`platform_run_steps` 自动补 `attempts/snapshot` 列，监控页显示「尝试 N 次」；`PLATFORM_FAIL_NODE_IDS` 可注入 stub 失败。实测失败节点尝试 3 次后运行失败且 trace 完整，开启回滚后输出回滚到 `revise-loop/verify-loop`（0.86）。详见 `docs/2026-10-30-执行器T1.4.md`。

#### [x] T1.5 调度器
- 调度依据：依赖就绪 + Agent 能力匹配度 + 当前负载 + 优先级。
- 输出：每个任务的 Agent 分配决策和理由（理由要能展示给评委）。
- **建议**：算法不用复杂，加权打分即可：`score = 0.5*能力匹配 + 0.3*(1-负载) + 0.2*优先级`。关键是**决策可解释**，不是算法多先进。
- 验收：同一批任务，调度日志能说明"为什么选了这个 Agent"。
- 完成记录：`server/platform/scheduler/scheduler.ts` + `/api/platform/scheduler`、`POST /api/platform/schedule`；按拓扑波次调度，能力标签包含匹配、批次内负载预占、优先级加权；每个决策输出中文理由、得分拆解、匹配能力、负载、次选 Agent，未分配任务给出能力缺口，阻塞任务列出未满足依赖。实测 8 任务课堂批次逆序提交仍按 `lesson → student-top → student-silent → observer → verify → report` 排序，观察员满载时得分为 0.63 且理由写明 1/1 负载。另修复"省略 `allowedAgentIds` 被解析成空数组导致全部 Agent 被排除"的真实 bug，并补回归测试。详见 `docs/2026-10-30-调度器T1.5.md`。

#### [x] T1.6 Self-Loop 控制器
- 循环：执行 → 验证 → 定位问题 → 修正（改 prompt/换工具/改路径）→ 再验证。
- 收敛条件：分数 ≥ 阈值、或达到最大轮次、或连续两轮无提升、或超预算（token/时间）。
- **建议**：修正动作只做三种（重写输出、换 Agent、补检索），不要做"工作流自动改写"，风险高、演示效果差。
- 验收：主链路能看到 2 轮迭代记录和分数变化。
- 完成记录：`server/platform/selfLoop/controller.ts` + `GET /api/platform/self-loop`；六种停止原因按 `passed → max_iterations → no_improvement → budget_time → budget_tokens → while_false` 判定，三种修正动作 `rewrite / swap_agent / retrieve`，换 Agent 直接复用 T1.5 调度器按当前能力标签选人并排除原 Agent。DSL 新增 `patience`（连续无提升容忍，1–10）与 `budget.maxDurationMs / maxTokens`；执行器每轮把修正指令注入后续 Agent 的 `selfLoop` 输入（带轮次、分数、问题清单、修正动作），并累计 token。实测课堂主链路 0.62 → 0.74 → 0.86，2 轮后 `stopReason = passed`，循环内消耗 1123 tokens；弱 Agent 探针展示 rewrite → rewrite → swap_agent（弱→弱→资深）；初始分已达标时 0 轮直接跳过。37 个平台测试全绿，监控页与画布均显示轮次、动作、分数变化。详见 `docs/2026-10-30-自循环T1.6.md`。

#### [x] T1.7 Verifier
- 三层：规则校验（格式/引用/必填）→ 交叉验证（≥2 个 Agent 独立打分）→ 基准比对（与 rubric/标准答案比）。
- 输出：总分、各维度分、置信度、问题清单、证据引用。
- **建议**：置信度用"多 Agent 分数方差"折算，公式写进方案书，评委就认。
- 验收：同一输出跑两次，分数波动 < 0.1；故意给错答案，能指出问题。
- 完成记录：`server/platform/verify/verifier.ts` + `GET /api/platform/verify`；规则层检查输出非空、`required` 必需内容、占位符、证据引用、`minChars`；交叉验证默认选主验证器 + 最多 2 个带 `verify.rubric` 的 Agent，独立按 rubric 打分，置信度按验证器总分标准差折算（单验证器上限 0.5）；基准层对照 `expectedKeywords` 列缺失要点。公式 `score = 交叉分 × (0.5+0.5×规则分) × (0.6+0.4×基准覆盖率)`。执行器自动把最近非验证节点输出作为被验证产物、汇总全运行 citations 作为证据，`platform_verify_results` 新增 `detail` 列存三层明细。实测主链路连续两次运行分数完全一致（0.62 → 0.74 → 0.86，验证器 0.88/0.84，分歧 0.02，置信度 0.94）；错误答案探针得分 0.3255，指出缺少「教学目标」与标准要点「分层练习」；监控页展示规则/交叉/基准三层与每名验证器分数。45 个平台测试全绿。详见 `docs/2026-10-30-验证器T1.7.md`。
