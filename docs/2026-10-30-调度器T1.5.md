# T1.5 调度器：能力匹配 + 负载 + 优先级

日期：2026-10-30
状态：已完成

## 1. 调度器解决什么问题

工作流只说明"有哪些任务、谁依赖谁"，不说明"每个任务交给哪个 Agent"。调度器读取注册中心里的 Agent 能力画像，为一批任务给出**可解释的分配决策**：

- 哪个任务分给哪个 Agent；
- 为什么选它（能力匹配、当前负载、优先级各自多少分）；
- 为什么没选别人（次选 Agent 是谁、差多少分）；
- 哪些任务暂时不能调度（依赖未完成）；
- 哪些任务没人能接（能力缺口）。

调度器只做计划，不执行。执行仍由 `WorkflowExecutor` 负责，两者通过 Agent id 对接。

## 2. 输入与输出

输入：

- `tasks`：任务 id、标题、所需能力标签、优先级（0–1）、`dependsOn`、可选 `allowedAgentIds`。
- `agents`：注册中心 `platform_agents` 中的启用 Agent 及其能力权重。
- 可选 `loads`：每个 Agent 的 `inFlight / capacity`，用于批次内负载均衡。
- 可选 `completedTaskIds`：已经完成的任务，作为依赖就绪的起点。
- 可选 `weights` / `reserve`：权重覆盖与是否在批次内预占负载。

输出 `SchedulePlan`：

```ts
{
  batchId, formula, weights,
  decisions: [{ taskId, agentId, score, breakdown, matchedCapabilities,
                missingCapabilities, load, reason, alternatives }],
  blocked:   [{ taskId, blockedBy, reason }],
  unassigned:[{ taskId, reason, candidates }],
  stats: { taskCount, scheduledCount, blockedCount, unassignedCount }
}
```

## 3. 算法

加权打分：

```
score = 0.5 × 能力匹配 + 0.3 × 可用度 + 0.2 × 优先级
可用度 = 1 - min(inFlight / capacity, 1)
```

- **能力匹配**：对任务要求的每个标签，在 Agent 能力表里做不区分大小写的包含匹配（支持中文标签），取权重最高的一项；最终取所有要求标签的平均权重。没有能力要求的通用任务按 0.5 处理。
- **依赖就绪**：按拓扑波次调度，`dependsOn` 中的任务必须已完成或已排入本批次；否则进入 `blocked` 并列出未满足的依赖。
- **批次内负载**：每次分配后给该 Agent 的 `inFlight + 1`，同批后续任务会看到新的可用度，从而自然分摊到空闲 Agent。
- **优先级**：任务自身优先级，只影响同批任务的排序与得分，不破坏依赖顺序。
- **可解释性**：每个决策都带中文 `reason`，例如：
  `选择 课堂观察员 Agent：能力匹配 0.90（参与度诊断 0.90），可用度 0.00（负载 1/1），优先级 0.90，综合得分 0.63；无其他候选。`
  有多个候选时会追加"次选 Agent（分数）"。

## 4. 接口

- `GET /api/platform/scheduler`：返回公式、默认权重、启用 Agent 数、可用能力标签全集。
- `POST /api/platform/schedule`：请求体 `{ tasks, loads?, completedTaskIds?, weights?, reserve? }`，返回 `{ plan }`。
- 请求校验：任务 id 必填且唯一、能力标签非空、优先级与权重在 0–1、`loads.inFlight >= 0`、`capacity >= 1`；不合法返回 400。

## 5. 实测

隔离服务：`PORT=8899 PLATFORM_DB_PATH=/tmp/yiban-t15/platform.db`。

课堂批次（8 个任务，故意逆序提交）：

```
order: lesson → student-top → student-silent → observer → verify → report
lesson          → lesson-plan-agent         0.94
student-top     → student-top-agent          0.87
student-silent  → student-silent-agent       0.85
observer        → classroom-observer-agent   0.63（人为设负载 1/1，可用度 0.00）
verify          → observer-verifier          0.91
report          → teaching-report-agent      0.89
blocked:    stuck ← not-scheduled
unassigned: quantum（没有 Agent 具备「量子教学」）
```

- 依赖顺序正确：即使 `report` 最先提交，也会排在 `verify` 之后。
- 负载生效：观察员 Agent 满载后得分为 0.63，仍被选中是因为它是唯一具备该能力的 Agent；理由里明确写出"负载 1/1"。
- 能力缺口可见：`quantum` 给出未分配原因，并附候选 Agent 缺失的能力标签。
- `allowedAgentIds` 限制生效：允许教研专家接"教学法评审"时选中它；让它接"教学设计"时明确报告能力缺口。
- 非法请求：重复 id 返回 400 `任务 id 重复：a`；空任务数组返回 400。

测试：`server/platform/scheduler/scheduler.test.ts` 7 条，覆盖能力择优与理由、学生人格映射、依赖顺序与阻塞、负载分摊与预占、停用 Agent 与能力缺口、可选数组省略、请求校验。`npm run test:platform` 共 28 条全通过。

## 6. 边界

- 当前调度器是**独立规划接口**，尚未自动驱动 `WorkflowExecutor`；把计划交给执行器是 T1.6 Self-Loop 的接入点。
- 能力匹配是标签包含匹配，不做语义向量匹配；对当前中文能力标签足够，后续可替换为 embedding 相似度。
- 负载由调用方传入（`loads`），尚未从运行中的 trace 自动汇总；批次内预占已实现。
- 调度计划暂不落库，`batchId` 仅用于本次响应；T1.8 指标页需要时再持久化。
