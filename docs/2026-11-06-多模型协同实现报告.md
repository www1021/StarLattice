# 多模型协同实现报告（P0 / P1 / P2）

日期：2026-11-06
范围：StarLattice / YiJiaoXun 平台内核（不改变教育、经营分析等场景内容）
验收：`npm run test:platform` 170/170 通过；`npm run build` 通过；服务端与前端 TypeScript 检查无错误。

## 1. 结论

平台此前实现的是“多 Agent”，不是真正的“多模型”：`agent.model` 能保存、能在页面上看到，但执行时被忽略；live Agent、工具调用和验证器都直接使用 `getPlatformLiveModel()`；只有 `llm` 节点支持节点级覆盖。因此 trace 里所有 Agent 实际调用的是同一个上游模型。

本轮把“角色分工”和“上游模型”解耦，完成三件事：

1. **P0 模型目录与路由**：建立逻辑模型目录，按“节点模型 → Agent 模型 → 全局默认”解析；验证器可用独立模型；未知模型显式回退，不静默替换。
2. **P1 异构验证与 Self-Loop 换模型**：执行侧可用快速模型、诊断/修订用推理模型、验证器用独立模型；Self-Loop 新增 `swap_model`，下一轮真实切换模型并记录 `fromModel → toModel` 与分数变化。
3. **P2 模型感知调度与预算**：调度任务可声明模型标签与成本上限，规划器会把诊断/修订角色的模型约束提升为调度约束；运行 token 超预算时高成本模型自动降级到 `fast`，并写入 trace。

需要明确的边界：**只有把不同逻辑 id 配到不同上游模型或不同供应商，才是真正的异构多模型**。默认环境中 `fast`、`reasoning`、`verifier` 仍跟随 `PLATFORM_LIVE_MODEL`，此时是“逻辑分层”，不是“模型异构”。

## 2. 改造前的问题

| 问题 | 具体表现 |
|---|---|
| Agent 模型字段是展示字段 | `agent.model` 落库并在注册中心展示，但 live handler 不读取 |
| 全局硬编码 | `runLiveAgent` / `runLiveLlm` / `liveScorer` 统一调用 `getPlatformLiveModel()` |
| 无法异构 | 执行、诊断、验证只能共用同一个上游模型，无法形成“快模型执行、强模型诊断、独立模型验证” |
| 验证不独立 | 验证器和被验证 Agent 使用同一模型，交叉验证容易同源偏差 |
| 无回退可见性 | 模型名写错时没有明确 fallback 标记，trace 无法判断实际用了什么 |
| 调度不看模型 | planner 只按能力、可用度、优先级分配，诊断节点可能被分给快速模型 |

## 3. P0：逻辑模型目录与统一路由

### 3.1 模型目录

新增 [`server/platform/models/catalog.ts`](../server/platform/models/catalog.ts)：

- `ModelProfile`：`id`、`label`、`description`、`provider`、`model`、`baseUrl`、`apiKey`、`tags`、`costTier`、`custom`。
- 内置逻辑 id：`platform-default`、`fast`、`reasoning`、`verifier`、`vision`、`minimax`。
- `PLATFORM_MODEL_CATALOG` 支持注册任意 OpenAI 兼容模型；同 id 覆盖内置档案。
- 环境变量可写逻辑 id 作为别名（例如 `PLATFORM_VERIFY_MODEL=minimax`），别名会继承目标档案的 provider、baseUrl 与 Key，不会把 `"minimax"` 当成 Qwen 模型名发给上游。

### 3.2 解析顺序

```text
Agent 节点：node.model → agent.model → platform-default
LLM 节点： node.model → platform-default
验证节点： node.model → 验证 Agent.model → PLATFORM_VERIFY_MODEL → verifier → platform-default
```

- `resolveAgentModel()`、`resolveModel()`、`resolveVerificationModel()` 统一实现上述顺序。
- **未知模型**：运行时默认按上游模型名直连默认 provider，但标记 `source: "fallback"` 与 `modelFallback`；`allowRaw: false` 时回退 `platform-default` 并写明原因。
- **Agent 保存校验**：`validateAgentModel()` 只接受目录中的逻辑 id，未知 id 返回 **422**，提示可用模型与 `PLATFORM_MODEL_CATALOG` 注册方式。

### 3.3 Provider 抽象

[`server/qwenOpenAiClient.ts`](../server/qwenOpenAiClient.ts) 增加 `provider: { baseUrl, apiKey, label }`，聊天与工具调用都按解析结果选择供应商。当前执行层支持 OpenAI 兼容协议；MiMo 使用 Anthropic 协议，未纳入本轮 provider 适配。

### 3.4 Trace 证据

每个 live 步骤输出统一包含：

| 字段 | 含义 |
|---|---|
| `model` / `resolvedModel` | 实际发给上游的模型名 |
| `requestedModel` | 配置中请求的逻辑 id 或原始模型名 |
| `modelProfile` | 命中的逻辑档案 id |
| `modelProvider` | 实际供应商 |
| `modelSource` | `default` / `node` / `agent` / `verifier` / `fallback` / `budget-downgrade` |
| `modelFallback` | 未知模型回退说明 |
| `modelDowngraded` | 预算降级来源与原因 |

### 3.5 内置 Agent 的异构分配

30 个内置 Agent 的默认模型分配为：

| 模型档位 | 数量 | 角色示例 |
|---|---|---|
| `fast` | 14 | 规划、检索、初稿、学生模拟、课堂观察 |
| `reasoning` | 8 | 经营诊断、经营修订、教研分析、选题分析 |
| `verifier` | 6 | 质量验证、课堂交叉验证、经营复核、选题评审 |
| `platform-default` | 2 | 教案生成、通用报告 |

种子回填只更新“版本为 1、`model='platform-default'`、创建时间等于更新时间”的原始内置记录，不覆盖用户已修改的 Agent。

### 3.6 节点与界面

- `AgentNode.model`、`VerifyNode.model` 加入 DSL 解析与编译契约。
- 节点配置新增“节点模型覆盖”“验证器模型”下拉框，选项来自模型目录。
- 新增 `GET /api/platform/models`，只返回展示字段，不返回 `apiKey` / `baseUrl`。
- 注册中心 Agent 卡片显示模型档案徽标；运行监控、验证报告、画布循环记录显示实际模型或 `from → to`。

## 4. P1：异构验证与 Self-Loop 换模型

### 4.1 验证器独立模型

- [`server/platform/verify/verifier.ts`](../server/platform/verify/verifier.ts)：每个验证 Agent 的评分结果写入 `model`、`resolvedModel`、`modelProvider`、`requestedModel`、`modelSource`。
- [`server/platform/verify/liveScorer.ts`](../server/platform/verify/liveScorer.ts)：按验证模型解析结果调用上游，缓存 key 同时包含逻辑 id 与上游模型，避免不同模型命中同一缓存。
- 支持 `budgetExceeded`：预算超限时验证模型同样按成本策略降级。

### 4.2 Self-Loop `swap_model`

[`server/platform/selfLoop/controller.ts`](../server/platform/selfLoop/controller.ts)：

- 新增动作 `swap_model`（界面“换模型”）。
- 模型诊断可返回 `nextModelId`；只接受目录中已知且不同于当前模型的 id，否则退回 `rewrite`。
- 兼容 `upgrade_model` / `switch_model` / `change_model` 别名。
- 启发式在连续停滞时优先尝试升级模型；**只有当前模型与 `reasoning` 实际解析到不同上游模型时才换模型**，否则继续换 Agent，避免“只改标签、不改实际模型”。

[`server/platform/runtime/executor.ts`](../server/platform/runtime/executor.ts)：

- 循环帧维护 `modelOverrides`、`currentModelId`、`previousModelId`、`modelSwitches`。
- 切换在上一轮结束时决定、下一轮生效；下一轮 Agent 节点使用覆盖后的模型。
- `platform_loop_iterations` 新增 `model_before` / `model_after`；旧库通过 `PRAGMA table_info` + `ALTER TABLE` 自动迁移。
- 循环摘要新增 `modelSwitches: [{ iteration, fromModel, toModel, reason, scoreBefore, scoreAfter }]`。
- 修订指令包含 `modelId` 与 `previousModelId`，便于 live prompt 说明本轮执行模型。

## 5. P2：模型感知调度与预算降级

### 5.1 调度模型标签

[`server/platform/scheduler/scheduler.ts`](../server/platform/scheduler/scheduler.ts)：

- 任务可声明 `modelTags` 与 `maxCostTier`。
- 声明 `modelTags` 时，评分追加 `0.15 × 模型匹配` 并归一化；未声明时权重为 0，旧任务分数保持不变。
- 没有模型标签匹配的候选直接排除；全部候选都超过成本上限时保留最低成本候选，并在理由中标记“超过任务成本上限”，避免任务卡死。
- 决策新增 `model` 与 `breakdown.model`，理由包含模型档案与成本档位。

[`server/platform/scheduler/planner.ts`](../server/platform/scheduler/planner.ts)：

- `diagnose` / `revise` 节点的 Agent 模型若带 `reasoning` 或 `verifier` 标签，自动提升为调度约束，避免诊断角色被分给快速模型。
- `PLATFORM_SCHEDULE_MAX_COST=low|medium|high` 为整批任务设置成本上限。

### 5.2 运行预算与降级

- `ExecutionContext` 增加 `tokensUsed` / `tokenBudget`。
- `PLATFORM_RUN_TOKEN_BUDGET` 配置运行级 token 预算；执行器输出 `tokenBudget` 与 `budgetExceeded`。
- 超预算后，`resolveModel()` 把非低成本模型降级到 `fast`，记录 `source: "budget-downgrade"` 与 `modelDowngraded.from`。
- Agent、LLM、验证器三处 live 调用共用同一降级逻辑。

## 8. 实测与未实测

### 已实测

- 全部单元测试与构建在本地通过。
- 模型路由、回退、预算降级、验证器独立模型、Self-Loop 换模型、调度模型标签均有行为级测试。
- 前端生产构建通过，模型目录 API 与界面类型检查通过。

### 本轮未执行

- **没有执行真实计费的“单模型 vs 角色路由”对照运行**。原因是本轮按低 token 成本策略，用 stub 单测与构建完成功能验收；真实对照需要多次上游调用，建议放在里程碑验收时执行。
- **没有接入 MiMo 的 Anthropic 协议**。当前 provider 只支持 OpenAI 兼容协议，MiMo 需要单独的协议适配层。

### 建议的真实对照方式

1. 准备两套环境变量：
   - 单模型：所有逻辑档位都指向 `qwen3.8-flash`。
   - 角色路由：`PLATFORM_MODEL_FAST=qwen3.8-flash`、`PLATFORM_MODEL_REASONING=<更强模型>`、`PLATFORM_VERIFY_MODEL=<独立模型>`。
2. 用同一条 `business-analysis-v1` 输入各跑一次，限制 `PLATFORM_RUN_TOKEN_BUDGET`，记录：
   - 首验分数与复核分数；
   - 循环轮数与 `stopReason`；
   - 各步骤 `modelProfile` / `resolvedModel`；
   - token 与耗时。
3. 对照结果写入 `benchmarks/results/`，不要只看“是否通过”，还要看验证器分歧与成本变化。

## 10. 后续建议

1. **补 MiMo / Anthropic 协议适配**，让 provider 抽象覆盖非 OpenAI 兼容供应商。
2. **补一次真实角色路由对照**，把“单模型 vs 角色路由”的分数、token、耗时写入基准报告。
3. **让模型目录可编辑**：当前通过环境变量与 JSON 注册；后续可在注册中心做模型档案的增删改与连通性测试。
4. **把模型成本纳入运行统计**：当前按 token 预算降级，尚未按价格累计成本；若比赛需要展示“成本优化”，建议补充单价与成本汇总。
5. **保持验证独立性**：生产配置中不要让 `verifier` 与执行侧落到同一上游模型；否则交叉验证仍可能同源偏差。
