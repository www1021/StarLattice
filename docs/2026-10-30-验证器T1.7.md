# T1.7 三层验证器

> **2026-11-06 更新**：Self-Loop 已改为模型驱动自愈，stub 不再模拟“修订后抬分”。本文的 0.62 → 0.74 → 0.86 属于旧 stub 演示数据，已被 [`2026-11-06-自愈A+C实现报告.md`](./2026-11-06-自愈A+C实现报告.md) 的 live 证据取代。  
> 目标：让"分数"可解释、可复现、可被追问。
> 代码：`server/platform/verify/verifier.ts`；执行器接入：`server/platform/runtime/executor.ts`。

## 1. 为什么需要三层

T1.6 之前，验证只有一个分数和一段问题文本。评委最容易追问的三个问题是：

- 这个分数是谁给的？→ 交叉验证层回答：至少两名验证 Agent 独立打分。
- 为什么不是随便编的？→ 规则层回答：格式、必需内容、证据引用是确定性检查。
- 有没有对照标准？→ 基准层回答：与标准要点逐项比对，缺什么直接列出来。

三层各做一件事，不互相替代：

| 层 | 检查方式 | 是否确定性 | 产出 |
|---|---|---|---|
| 规则校验 | 输出非空、必需内容、占位符、证据引用、最小篇幅 | 是 | `rule.score` + 每项 `checks[]` |
| 交叉验证 | ≥2 名验证 Agent 按 rubric 独立打分 | 打分器可替换 | `crossCheck.score` + 每人分数 + 分差 |
| 基准比对 | 与 `expectedKeywords` 标准要点逐项对照 | 是 | `baseline.coverage` + 命中/缺失要点 |

## 2. 分数与置信度

```
score = 交叉验证分 × (0.5 + 0.5 × 规则分) × (0.6 + 0.4 × 基准覆盖率)
confidence = clamp(1 - 3 × 验证器总分标准差, 0.2, 0.98)
```

- 交叉验证分是基础分；规则层和基准层是**否决项**，不通过就按比例压低分数，不会凭空抬高。
- 规则分 = 通过项 / 总检查项。比如 4 项过 3 项 → 0.75。
- 未配置 `expectedKeywords` 时基准覆盖率记为 1（中性），不惩罚没有标准答案的工作流。
- 置信度只由验证器之间的分差决定：分差 ≤ 0.1 记为一致；只有 1 名验证器时置信度上限 0.5，并输出"交叉验证降级"问题；规则或基准明显失败时置信度上限 0.65。

## 3. DSL 新增字段

`verify` 节点新增 5 个可选字段，画布抽屉会自动渲染：

| 字段 | 类型 | 作用 |
|---|---|---|
| `verifiers` | string[] | 交叉验证 Agent 列表；留空时自动选"主验证器 + 最多 2 个带 `verify.rubric` 工具的 Agent" |
| `required` | string[] | 规则层：输出必须包含的字段或小节名称 |
| `expectedKeywords` | string[] | 基准层：标准答案关键词，缺失会进问题清单 |
| `minChars` | number | 规则层：正文最少字符数，0 或不填表示不检查 |
| `requireEvidence` | boolean | 是否要求证据引用；留空时按 rubric 是否含"证据/引用/来源"自动判断 |

示例：

```json
{
  "id": "check",
  "kind": "verify",
  "verifier": "observer-verifier",
  "verifiers": ["observer-verifier", "teaching-expert-agent"],
  "rubric": ["目标达成", "互动覆盖", "证据支撑"],
  "threshold": 0.85,
  "required": ["教学目标", "学生活动"],
  "expectedKeywords": ["分层练习"],
  "minChars": 200
}
```

## 4. 执行器如何接入

1. **自动找被验证对象**：验证节点没有显式映射 `artifact` 时，默认验证最近一个非验证节点的输出；循环里就是 `revise` 的输出，主链路初始验证就是 `observer` 的输出。步骤输入会记录 `artifact`、`evidence`、`targetNodeId`，trace 上能直接看到验证的是谁。
2. **自动收集证据**：从本次运行所有节点输出里收集 `citations`，去重后最多 8 条，作为规则层"证据引用"检查和报告证据池。
3. **落库明细**：`platform_verify_results` 新增 `detail` 列（启动时自动补列），保存三层明细、每名验证器分数与被验证节点 id。
4. **运行输出**：`run.output.verify` 返回最后一次验证的 `score / confidence / passed / layers`，T1.12 报告页可直接消费。

## 5. 接口

- `GET /api/platform/verify`：返回契约、三层说明、公式与默认值。
- `GET /api/platform/health`：`verify` 字段返回同样的公式摘要。
- `GET /api/platform/runs/:id/trace`：`verifyResults[].detail` 携带三层明细。
- `GET /api/platform/node-types`：验证节点字段已更新，画布无需改代码即可编辑新字段。

## 7. 边界

- **stub 模式不模拟抬分（2026-11-06 起）**：`stubDimensionScorer` 只按产物内容、规则层和基准覆盖计算，同一份产物无论第几次验证都得到同一分数；置信度上限 0.50，并在问题清单标注「stub 演练」。stub 结果不能作为模型自愈证据。
- **live 模式默认使用 LLM 验证打分器**：启用 Qwen 时由 `createLlmDimensionScorer` 按 rubric 打分；未启用时回落到启发式（关键词、篇幅、规则分、覆盖率、能力标签）。三层结构和公式不变。
- 证据只认 `citations` 数组里的字符串或 `{title, source}`，不解析正文里的引用角标。
- 置信度是"验证器分差"的换算，不是统计意义上的置信区间。
- 暂无独立验证报告页（T1.12）与分数历史对比图。
