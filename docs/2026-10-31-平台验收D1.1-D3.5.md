## 2. D1.1 Self-Loop 最优产物保留

问题：循环最后一轮可能比历史轮更差，旧实现直接以最后一轮产物收尾。

改动：

- 执行器记录每轮产物与验证分，运行结束保留历史最优轮（`bestIteration`，0 表示初始产物），并回滚输出、验证报告与作用域变量。
- 回归测试覆盖「最后一轮更差」场景。

live 证据：

- `edu-07`（现在进行时）：B 0.772 未达标；C 循环 2 轮，保留最优产物后 0.913 达标。
- `edu-17`（化学方程式配平）：B 0.863；C 循环 2 轮后 0.915。

## 3. D1.2 运行前全局调度

- 打分：`0.5 × 能力匹配 + 0.3 × 可用度 + 0.2 × 优先级`，单 Agent 容量 1。
- 计划在运行创建时落库（`platform_runs.plan`），包含每个节点的分配、得分拆解、次选 Agent、阻塞与能力缺口；trace 与监控页可读中文理由。
- 30 用例运行中 90/90 次运行都带调度计划；并发压测中「有调度计划」覆盖率 100%。

## 4. D2.1 第二场景：论文选题评审

- 新增三套 DSL：单 Agent、固定流水线、完整平台（检索 → 三评审并行 → 汇总 → 验证 → 1 轮循环 → 报告），与教育场景共用同一编译器、执行器和三层验证器。
- 10 条选题用例覆盖正常、创新性不足、可行性不足、规范性不足。
- 验证节点改挂两个专用验证器：`topic-review-verifier`（评评审报告质量）与 `topic-review-auditor`（证据与覆盖核对）。此前沿用教案评审人设，等于让「提出选题意见的人」给自己打分，会把选题本身平庸误算成评审报告差；换人设后 A/B/C 在同一用例上恢复正确序关系（A 0.729 < B 0.963 ≈ C 0.963）。
- 结果：见第 8 节全量复测（专用验证器版本）。

## 9. 与验收标准的差距

未达项：难例子集 C 55.6% vs B 55.6%，差 0 个百分点（目标 +10pp）。

难例 9 条 = 教育 5（edu-10/12/18/19/20）+ 选题 4（topic-02/04/06/09）。教育难例 C/B 均 5/5；选题难例两者 0/4，因此差值被压平。

原因：

1. 0.85 阈值按教案产物设定，评审报告类产物在 live 验证下普遍落在 0.2–0.8，阈值未按场景校准。
2. live 验证方差大：同一 topic-04 在相同配置下多次运行得到 0.33、0.38、0.67 三种结果，单轮循环无法稳定收敛。
3. C 的选题报告由循环后单独生成，与 B 的固定收尾产物结构不同，验证方差会直接体现在分数上（edu-18 也是 C 略低于 B 的例子）。

已排除的「作弊式」修法（均实测无效，未采用）：

- 把选题 rubric 改名为「创新性判断/可行性判断/规范性判断」：0.335，无改善。
- 把验证器提示词改成「评产物完成质量」：0.380，规范性维度被打到 0，反而更差。
- 循环上限从 1 提到 2：0.419，token 从 62k 涨到 92k，仍未收敛。

下一步（按优先级）：

1. 选题验证校准：用人工锚点样本（好/中/差各 3 份）标定 rubric 与阈值，而不是按分数调参。
2. 降低验证方差：同一产物多次打分散度超阈值时取中位数或触发复评。
3. C 的收尾产物对齐：报告节点输出结构与 B 对齐，减少「同质产物不同分」。
4. 跨运行调度负载：把 in-flight 计入调度，兑现并发场景下的调度差异。

## 11. D3.4 失败案例

### 11.1 验证误判：把正常表述识别为占位内容

- 现象 1：教案写「心字底占位恰当」，规则层命中占位正则，静夜思三条基线全部判定失败（C 0.775）。
- 现象 2：选题评审报告里出现「模板中仍保留占位符，需要替换」这类元讨论，裸词「占位符」再次被判定为占位内容，规则分被压到 0.667。
- 原因：占位正则包含裸词「占位」「占位符」，无法区分「自身是占位」与「在讨论占位」。
- 处理：只匹配明确的占位标记（TODO、待补充、此处填写、【占位】等）和「占位符未替换/占位待替换」这类明确标记；裸词「占位符」不再命中，同时补充元讨论回归用例（`server/platform/verify/verifier.test.ts`）。
- 结果：占位单测 7/7 通过；本轮 rerun 的服务在规则修复前启动，个别提及「占位符」的样本仍按旧规则计分，审计报告中单列「占位误伤」列，不计入结论。
- 下一步：规则词表按学科语料回归，避免同类误伤。

### 11.2 循环产物与最终交付物不一致：选题完整平台

- 现象 1：循环救回了 topic-04（初始 0.813 → 修订 0.928），但修订稿只有 726 字，没有总体结论；如果直接验证循环产物，短修订稿会被当成最终交付物计分。
- 现象 2：为修此问题新增「报告终验」后暴露出更严重的一层：最终报告由 LLM 二次改写，topic-06 汇总 0.969，改写后的报告只有 0.500，topic-02/04/06 分别掉到 0.741/0.733/0.500。
- 原因：报告节点是第二次生成而非组装，模型会重写、压缩并丢掉证据与结论；同时 `${revise.output}` 在循环未执行时不存在，报告正文为空。
- 处理：终验挂在最终报告上，并设「结论 + 600 字」最低要求；报告节点改为确定性 `report.build`，正文原样继承最优产物，缺省回退到最近一次产物。
- 兜底：三层验证 + 规则层硬检查，异常分数不会让运行失败（运行成功率 100%）。
- 下一步：把必需内容升级为硬门槛；引用检查只认产物正文中的引用标记。

### 11.3 同质产物不同分：topic-03

- 现象：同一用例 topic-03，B 0.963、C 0.814，C 触发 1 轮循环（0.801 → 0.814）仍未达标。
- 原因：live 验证对结构与措辞敏感；C 的汇总由三份并行评审合成，信息密度高但结论表述不如 B 的固定模板稳定。
- 兜底：最优产物保留，循环不会让结果比初始更差；该用例如实记为 C 未达标，不做阈值下调。
- 下一步：验证器多次打分取稳健值；对结论/建议等结构项做确定性检查，减少措辞敏感。

### 11.4 验证器灵敏度不足：缺陷注入实验

- 方法：取 topic-01 的真实产物（2,666 字，原始验证分 0.965），按可控缺陷做定向删改，用同一套生产验证 Agent 重新打分，每个变体重复 2 次；样本与脚本为 `benchmarks/audit-verifier-sensitivity.ts`，报告为 `benchmarks/results/verify-sensitivity-latest.md`。
- 结果：删除引用标记与引用来源节 0.964（−0.001）；删除必须修改项与建议修改项 0.929（−0.036）；删除总体结论与开题判断 0.883（−0.082）；只保留前 60% 字句 0.963（−0.002）。
- 现象：验证分只对「结论缺失」有明显反应，对引用与建议缺失几乎不敏感；结论缺失后仍高于 0.85 阈值。
- 原因：交叉验证层按整体印象打分，偏向宽容；引用检查把「知识库证据池非空」也算作有引用，产物正文删掉引用仍能通过规则层。
- 已做 1：选题完整平台工作流新增「报告终验」节点，并对最终报告要求「结论」与最小篇幅 600 字，避免循环后的短修订稿被当成最终交付物计分。加上终验后立刻暴露第二个问题：最终报告由 LLM 二次改写，topic-06 的汇总 0.969、改写后的报告只有 0.500，等于把已经达标的内容改差了。
- 已做 2：把「生成评审报告」从 LLM Agent 改成确定性的 `report.build` 工具，正文原样继承最优产物，只追加标题与验证分；循环未执行时回退到最近一次产物，不再依赖不存在的 `${revise.output}`。改完后 topic-01 的终验分从 0.000（正文为空）恢复到 0.979。
- 改进方向：把必需内容设为硬门槛（任一缺失直接不通过），引用检查只认产物正文中的引用标记；两项都会改变评分语义，需连同回归用例一起改，本轮未做。
- 说明：该实验替代人工锚点，全部由脚本与模型完成，不需要人工标注。

## 12. D3.5 成本与延迟

- 单次运行平均 Tokens：A 9,396；B 26,086；C 39,742（C 约为 B 的 1.5 倍，主要来自循环与报告节点）。
- 成本公式：`成本 = Tokens / 1000 × PLATFORM_COST_PER_1K_TOKENS`，单价由部署方注入，不在代码里写死。
- 延迟：C P50 60.8s、P95 156.2s；B P50 57.2s、P95 124.3s；A P50 40.2s、P95 50.9s。
- 结论：C 用约 1.5 倍 token、约 1.1 倍 P50 换来平均分 +0.047、教育场景达标率 +10pp；选题场景提升 +0.109 但未达阈值。
