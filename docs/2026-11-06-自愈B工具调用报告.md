# 自愈 B（Function Calling）实现报告

日期：2026-11-06  
范围：B（模型工具调用自愈）  
状态：**已完成并通过 live 验证。**

## 1. 结论

诊断 Agent 不再接受平台预填的指标和口径规则，而是由模型自己决定「查什么、用哪个工具、传什么参数」：

1. 验证器发现毛额口径错误，首验 **0.5395** 未通过。
2. 诊断 Agent 在 **2 轮**内自主发起 **4 次工具调用**：
   - `knowledge_search` → 命中 3 篇口径资料；
   - `profile` → 读取订单数、退款额、净销售额等数据概况；
   - `metric_calc(gross)` → 复算毛额口径；
   - `metric_calc(net)` → 复算净额口径并对比差异。
3. 模型把工具返回的事实写入 `evidence`，输出 `revenueBasis=net` 的结构化诊断与 `promptPatch`。
4. 平台按模型选择的口径重算并重写报告，复核 **0.95** 通过（阈值 0.70），补丁晋升 `business-planner` **v1 → v2**。
5. 第二次运行直接采用 v2：**0 轮循环、首验 0.9166 通过**，规划 rationale 明确引用 v2 补丁。

这解决了硬伤 2 的具体形态——**旗舰 Self-Loop 不再是脚本按轮次抬分**：初始失败来自内容，修复动作来自模型，补丁可被下一次运行复用。

## 2. 实现内容

### 2.1 工具调用协议

- `server/qwenOpenAiClient.ts` 新增 `completeQwenToolChat`：支持 OpenAI 兼容的 `tools`、assistant `tool_calls` 与 `tool` 结果消息，返回 `content / toolCalls / finishReason`。
- `AgentNode` 新增 `toolCalling?: boolean`；DSL 解析、节点类型契约、客户端类型与经营分析模板同步。
- 只有显式开启的 Agent 节点才进入工具循环；未开启的节点保持原来的单轮文本补全。

### 2.2 工具目录与执行边界

`server/platform/runtime/liveHandlers.ts`：

- 只暴露 Agent 自己声明、且当前可执行的工具：
  - 内置 `knowledge.search`；
  - 注册中心里 `type=mcp` 且 `enabled=true` 的 MCP 工具；
  - `verify.rubric` 等非执行型内置工具会被跳过。
- MCP 工具 id 含点号，平台把函数名归一化为 `profile` / `metric_calc` 等安全名称，并保留 `工具 ID` 说明用于反向映射。
- 平台注入必要上下文，模型不能自选数据源或越权检索：
  - 知识库范围来自工作流绑定；
  - MCP `source` 默认取工作流输入 `source`，模型只生成业务参数（如 `revenueBasis`）。
- 最多 **4 轮**（`PLATFORM_AGENT_TOOL_ROUNDS`，上限 8）；达到上限后禁用工具再请求一次最终答复，避免死循环。
- 工具参数非法、未知工具、MCP 抛错都会作为工具结果回填给模型，由模型自行纠正；调用失败不会直接中断节点。
- 每次调用记录 `name / toolId / arguments / ok / latencyMs / summary / citations`，写入步骤产物与运行 trace。

### 2.3 旗舰流程改造

`business-analysis-v1.json` / `templates.ts` 的诊断节点：

- 开启 `toolCalling: true`。
- 删除预填的 `profile`、`metrics`、`rule` 输入，只保留报告正文、验证问题、用户问题与分析结果。
- Prompt 明确要求先调用 `knowledge_search`、`profile`、`metric_calc(gross/net)`，再输出诊断 JSON；`evidence` 必须引用工具返回的事实。

因此诊断中的口径判断与数字证据来自模型实际调用，而不是平台预先算好再喂给模型。

## 5. 对三个问题的直接回答

### 硬伤 2 是否解决？

**是，按原评审所指的具体形态已经解决。** 原问题是「Self-Loop 旗舰演示是脚本抬分」：

- 验证器不再按轮次抬分，同一产物同一分数；stub 置信度上限 0.50 并显式标注。
- 初始失败由内容与关键指标核对触发，而不是脚本制造。
- 诊断动作、工具选择、工具参数、修正补丁都由模型生成。
- 补丁不是一次性脚本，晋升后第二次运行直接复用。

### 是不是真正的模型自愈？

**是「可审计的模型自愈」，但不是「模型自己改代码」。** 准确边界：

- 模型负责：选择工具、生成参数、读取工具结果、定位根因、选择修复动作、撰写补丁。
- 平台负责：执行工具调用、限制可用工具与轮次、应用补丁、晋升/回滚 Agent 版本。
- 验证器负责：发现初始错误并判定修复是否达标。

这三者缺一不可。若宣称「模型完全自主发现并修复一切问题」则不诚实；当前实现是模型在受控工具与验证闭环内完成诊断和修复。

### 是否满足比赛要求？

**满足赛道 1「Agent 编排创新应用」对自愈与工具使用的要求，但答辩时仍需主动说明边界：**

- 已有：真实模型决策、真实 MCP/知识库调用、结构化诊断、可复用补丁、版本晋升与回滚、确定性验证门禁、完整 trace。
- 仍有：单次 live 成功样本，未做多次重复与方差统计；锚点验证只覆盖关键指标；补丁校验只拦截明显答案泄漏；知识库未导入时检索会返回空，诊断会退化到仅依赖 MCP。
- 建议答辩补强：同一失败输入重复跑 3–5 次，报告成功率与分数区间；这比再增加一个演示场景更能回应「结果验证与性能评估」维度。

## 6. 复现

```bash
cd StarLattice
PLATFORM_LIVE_AGENTS=1 PLATFORM_STEP_TIMEOUT_MS=180000 PORT=8791 npx tsx server/index.ts

# 回到 v1，制造可自愈的初始失败
curl -s -X POST http://127.0.0.1:8791/api/platform/agents/business-planner/rollback \
  -H 'Content-Type: application/json' -d '{"version":1}'

curl -s -X POST http://127.0.0.1:8791/api/platform/runs \
  -H 'Content-Type: application/json' \
  -d '{"workflowId":"business-analysis-v1","input":{"question":"按订单销售额口径看一下本期区域与品类毛利，为什么下滑？","source":"data/demo/sales.csv"}}'

# 查看诊断步骤的 toolCalls / citations
curl -s http://127.0.0.1:8791/api/platform/runs/<runId>/trace
```

当前演示库已晋升到 v2，直接运行会首验通过。要重复完整自愈链路，先回滚到 v1。
