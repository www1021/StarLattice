# T1.11 运行监控台

目标：把「运行」从一次性结果变成可观察、可重放的过程，满足赛题「结果验证与监控」模块的可视化要求。

## 交付内容

| 能力 | 实现位置 |
|---|---|
| 异步启动运行（202 + running 记录） | `server/platform/runtime/executor.ts` 的 `start()`；`server/platform/routes.ts` 的 `POST /api/platform/runs` |
| 整单重跑（按原输入新建运行） | `POST /api/platform/runs/:id/retry` |
| 单步重跑（追加步骤，不改原运行） | `WorkflowExecutor.retryStep()`；`POST /api/platform/runs/:id/steps/:stepId/retry` |
| 步骤错误保留堆栈 | `executor.ts` 的 `errorDetail()`，`platform_run_steps.error` 存 `error.stack` |
| stub 节奏放慢（演示用） | `PLATFORM_STUB_DELAY_MS`，仅 stub 模式，上限 5s/步 |
| 运行列表 + 时间线 + 单步 IO | `src/features/platform/RunMonitorPage.tsx` |
| 运行中实时刷新 | 画布运行弹窗 600ms 轮询 trace；监控页 900ms 轮询列表与 trace |
| 侧边栏入口 | `src/components/Sidebar.tsx`「运行监控」；`src/main.tsx` 的 `monitor` section |

## 交互说明

- **运行列表**：按开始时间倒序，展示状态点、工作流名、步数、耗时；运行中状态点脉冲。
- **时间线**：每条步骤显示 `path / #序号 / 节点类型 / 耗时 / 开始时间 / 状态`；失败步骤默认展开并显示堆栈。
- **单步输入/输出**：点「查看输入/输出」展开两侧 JSON，失败时同样可看已解析输入。
- **单步重跑**：任意已结束步骤都可重跑，红色按钮仅出现在失败步骤；重跑会追加一条新记录，**不改变原运行终态，也不向下游传播**，横幅会明确提示。
- **整单重跑**：按原输入新建一次运行并自动选中，适合演示「同一工作流重复跑」。
- **实时刷新**：存在 `running / queued / verifying / revising` 运行时自动轮询，全部终态后停止，右上角显示「轮询中 / 已同步」。

## 接口变更

```http
POST /api/platform/runs
{ "workflowId": "classroom-v1", "input": { ... }, "async": true }
→ 202 { "run": { "status": "running", ... } }

POST /api/platform/runs/:id/retry
→ 202 { "run": { ...新运行... }, "retryOf": "run_xxx" }

POST /api/platform/runs/:id/steps/:stepId/retry
→ 200 { "step": { ...新步骤... }, "trace": { run, steps, verifyResults, loopIterations } }
```

`POST /runs` 不传 `async` 时保持原有同步行为（返回 `{ run, steps }`），方便 curl 脚本与已有测试。

## 验收记录

环境：隔离栈 `PORT=8790 PLATFORM_DB_PATH=/tmp/yiban-monitor-test.db PLATFORM_STUB_DELAY_MS=600` + Vite 5174，headless Chrome 1440×900 通过 CDP 驱动。

1. **运行中实时刷新**：点击运行 2.2s 后，画布 trace 已有 6 条（5 成功 + 1 执行中），节点已上色；等待约 6s 后终态 12 条、0.86、2 轮。
2. **监控页聚合**：选中最新的成功运行，时间线 12 条、验证 3 次、循环 2 轮、总耗时 6020ms，与后端一致。
3. **单步 IO**：展开后输入/输出 `pre` 均有内容。
4. **单步重跑**：对 `retrieve` 重跑后步骤数 12 → 13，横幅提示「只追加一条记录，不改变原运行的最终状态与下游结果」，运行状态仍为成功。
5. **整单重跑**：运行数 +1，新运行运行中时监控页 1.8s 内已出现 6 条并刷新，终态 12 条。
6. **失败路径**（向临时库注入一条 failed 运行）：页面显示运行错误与完整堆栈（含 `at invoke (...)`），失败步骤默认展开、出现单步重跑按钮；重跑后新步骤成功，原运行仍为失败。
7. **控制台**：除浏览器自动请求 `/favicon.ico` 的 404 外无报错。

## 已知边界

- 实时刷新用轮询而非 WebSocket；单机演示足够，后续量大再换 SSE/WS。
- 单步重跑只重放该节点，不重算下游；真正的「从失败点继续」属于 T1.4 的回滚/重放。
- 失败注入依赖 T1.4 的重试与真实 Agent 报错；当前 stub 主链路不会自然失败，验收时用临时库注入或等 T1.4。
- `step_count` 会包含重跑追加的记录；「去重后的逻辑步数」留到 T1.8 指标采集时处理。

## 30 秒演示脚本

1. 打开「编排画布」→ 运行 → 输入课题，弹窗内状态从「运行中」变为「成功」，节点逐个变绿。
2. 切「运行监控」→ 最新运行已选中，时间线、验证分数、循环轮次一屏可见。
3. 展开某步输入/输出 → 点「单步重跑」→ 多出一条记录，横幅说明不改变原运行。
4. 点「整单重跑」→ 新运行出现并实时刷新，证明同一 DSL 可重复执行。
