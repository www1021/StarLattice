## 二、实验设计

### 2.1 五个实验臂

| 代号 | 名称 | 与现版本差异 | 作用 |
| --- | --- | --- | --- |
| A0 | 单 Agent 直出（历史） | 保持原样 | 只作下限参考，报告里明确标"无检索，不参与主结论" |
| A1 | 单 Agent 公平版 | 新增 `retrieve → agent`，同样拿知识库和引用要求 | 证明"不是能力差，是以前没给它检索" |
| B | 固定流水线 | 保持原样 | 主对照 |
| C | 完整平台 | 保持原样 | 主实验 |
| C−loop | 完整平台去 Self-Loop | 只删 `revise-loop` 节点，其余（检索、多评审/多角色、验证、观察员、报告）全部保留 | 证明增益是否来自循环 |

关键：C−loop 不是退化成 B。以教育场景为例，B 是 `retrieve → lesson-plan → verify → rehearse → observer → report`；C−loop 是 `retrieve → lesson-plan → verify-initial → rehearse → observer → report`，保留了初始验证与完整多角色链路，差别只有修正回路。

### 2.2 统一任务契约

同一场景下，所有实验臂收到**相同的交付要求**，否则裁判会惩罚"没被要求写的东西"：

- 选题：报告必须含 `总体结论 / 必须修改项 / 建议修改项 / 引用来源` 四节，至少 2 条可追溯引用，正文 ≥1200 字。
- 教育：沿用现有 rubric（目标达成、互动覆盖、证据支撑），至少 1 条可追溯引用。
- 达标线统一 0.85。

A1/B 的提示词要补齐同样的四节与引用要求；C 现有的 `report.build` 已满足。

### 2.3 固定裁判（核心改动）

新增 `benchmarks/judge.mjs`，从运行 trace 里取**最终产物**，用固定裁判打分，不再读各工作流自己的 `verify`：

1. 确定性层（无需 Key，可复现）：非空、`minChars`、`requiredSections`、引用标记与证据池绑定、占位符、数字一致（适用时）。
2. 模型层：固定 judge 模型、`temperature=0`、固定 rubric、`evidenceView=cited`（只给产物实际引用的证据，避免"池里有就算过"）。
3. 输出两列，永不混用：
   - `evalScore`：固定裁判分，用于所有横比与达标率。
   - `selfVerifyScore`：工作流内部验证分，只用于分析"自验是否虚高"。
4. judge 模型必须写进报告头，并单独统计 judge Tokens。

## 六、验收标准

一份新报告必须同时满足：

1. A1 不再是 0%，且与 A0 的差距能说明"检索与公平性"的影响。
2. C vs B：给出逐用例配对结果与 Δ 的 95% 区间；难例子集单列。若仍是 +0.0，报告直接写"本数据集上无增益"，不辩解。
3. C vs C−loop：给出循环的边际贡献。若 ≤0，就把 Self-Loop 的主张改成"提升修订效率/分数稳定性"，不再宣称提升达标率。
4. 主表只用 `evalScore`；`selfVerifyScore` 只出现在"自验偏差"一节。
5. 报告头含：日期、模式（live/stub）、模型（含 judge）、工作流版本、臂数、用例数、真实总耗时。
6. 并发结论不超过实际测过的范围。
