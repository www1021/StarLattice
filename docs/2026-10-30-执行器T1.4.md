# T1.4 运行时执行器

目标：把执行器从「顺序跑完 + 失败即终止」升级为带状态机、单步超时、指数退避重试、快照回滚和失败注入的可演示运行时，对应赛题「任务调度与执行」与「结果验证与监控」。

## 交付内容

| 能力 | 实现位置 |
|---|---|
| 运行状态机：queued → running → verifying / revising → succeeded / failed / rolled_back | `server/platform/runtime/executor.ts` 的 `execute()` / `setStatus()` / `finish()` |
| 单步超时 | `invokeWithTimeout()`，默认 30s，可关 |
| 指数退避重试 | `runStepBody()` + `retryDelay()`，默认 3 次、200ms 起、上限 2s |
| 每步快照 | 成功步骤写 `platform_run_steps.snapshot` |
| 失败回滚 | `rollbackToSnapshot()` 恢复最近一次成功快照，运行标记 `rolled_back` |
| 并行分支收敛 | 并行分支改为 `Promise.allSettled`，全部结束再决定失败，避免后台残留写入 |
| 失败注入（演示） | `PLATFORM_FAIL_NODE_IDS`，仅 stub 模式，指定节点抛错 |
| 尝试次数落库与展示 | `platform_run_steps.attempts`；监控页显示「尝试 N 次」 |
| 旧库自动迁移 | `ensureStepColumns()` 启动时补 `attempts` / `snapshot` 两列 |
| 运行时配置可见 | `GET /api/platform/health.runtime` |

## 运行参数

| 环境变量 | 默认 | 范围 | 说明 |
|---|---:|---:|---|
| `PLATFORM_STEP_MAX_ATTEMPTS` | 3 | 1–10 | 单步最多尝试次数（含首次） |
| `PLATFORM_STEP_TIMEOUT_MS` | 30000 | 0–600000 | 单次尝试超时；0 关闭 |
| `PLATFORM_RETRY_BASE_MS` | 200 | 0–10000 | 第 2 次尝试前等待 |
| `PLATFORM_RETRY_MAX_DELAY_MS` | 2000 | 0–60000 | 退避上限 |
| `PLATFORM_ROLLBACK_ON_FAILURE` | false | true/false | 重试耗尽后回滚到最近成功快照 |
| `PLATFORM_FAIL_NODE_IDS` | 空 | 逗号分隔节点 id | stub 模式失败注入，如 `report` |

也可以直接给 `new WorkflowExecutor(store, handlers, options)` 传同名驼峰参数，测试用这种方式避免读环境变量。

## 状态机

```
queued ──执行开始──> running
                        ├─ verify 节点开始 ──> verifying ──结束──> running
                        ├─ loop 每轮开始 ────> revising  ──body 结束──> running
                        ├─ 全部节点成功 ─────> succeeded
                        ├─ 重试耗尽 ─────────> failed
                        └─ 重试耗尽且开启回滚 -> rolled_back
```

- `queued` 在 `createRun()` 时落库，异步启动接口会先返回排队记录，随后轮询看到 `running`。
- `verifying` / `revising` 通过 `updateRunStatus()` 实时写入，监控台轮询可见。
- `onStatusChange` 可选回调把每次状态变化推给调用方，测试用它断言完整链路，后续可接 WebSocket。

## 重试与超时

- 每次尝试失败后等待 `base × 2^(n-2)`，再重试；同一行步骤记录复用，`attempts` 写最终次数。
- 失败步骤保留**最后一次**错误的完整堆栈；前面尝试的失败不单独成行，避免污染时间线。
- 超时用 `Promise.race` 实现，错误信息为「步骤执行超时（>Nms）」；底层 handler 不强制中断（无 AbortSignal），超时后其结果被忽略。
- 重试成功时 `error` 清空、`attempts` 保留实际次数，方便区分「一次过」和「重试后过」。

## 快照与回滚

- 每个成功步骤写入 `{ outputs, verifyRounds, lastVerifyScore }` 快照；快照不返回给前端，避免 trace 体积膨胀。
- 失败且 `rollbackOnFailure=true` 时，恢复最近一个成功步骤的快照，运行状态置为 `rolled_back`，输出记录：

```json
{
  "mode": "stub",
  "rolledBackTo": "revise-loop/verify-loop",
  "stepId": "c978b6c6-...",
  "score": 0.86
}
```

- 只做「恢复到上一步快照」，不做反向执行，符合 TODO 的简化建议。

## 验收记录

环境：隔离栈 `PORT=8899 PLATFORM_DB_PATH=/tmp/yiban-t14/platform.db`。

1. **正常主链路 + 实时状态**：`PLATFORM_STUB_DELAY_MS=60`，异步运行 classroom-v1，轮询记录到
   `running → verifying → revising → verifying → revising → verifying → running → succeeded`；
   12 条步骤、验证 3 次（0.62/0.74/0.86）、循环 2 轮、总耗时 621ms。
2. **失败注入 + 重试**：`PLATFORM_FAIL_NODE_IDS=report PLATFORM_RETRY_BASE_MS=20`，运行最终 `failed`，`report` 步骤 `attempts=3`，错误首行为 `Error: [stub] 注入失败：节点 report`，前 11 步正常保留。
3. **回滚**：追加 `PLATFORM_ROLLBACK_ON_FAILURE=true`，同一失败运行最终 `rolled_back`，输出 `rolledBackTo = revise-loop/verify-loop`、`score = 0.86`，失败步骤仍保留在 trace。
4. **监控页**：headless Chrome 打开运行监控并选中失败运行，时间线显示「#12 · 工具 · 99 ms · 尝试 3 次」，错误框显示注入原因；控制台无报错。
5. **旧库迁移**：启动时 `PRAGMA table_info` 检查并自动补 `attempts` / `snapshot`，无需删 `data/platform.db`。

## 已知边界

- 重试策略是运行级配置，节点级 `retry` / `timeout` 尚未进入 DSL（避免现在改画布契约）。
- 超时只让运行时放弃等待，不能强行中止正在执行的 handler；真实 LLM 调用应在 handler 内部配合 AbortSignal。
- 快照是整份上下文的完整拷贝，演示规模足够；大输出场景需要改成增量或引用。
- 回滚是「恢复到快照 + 标记状态」，不会撤销已产生的验证/循环日志；单步重跑后的下游重算仍属于后续任务。
- 并行分支现在等全部结束再失败；没有取消机制，慢分支会拖长失败路径。
- 失败注入只对 stub 生效，真实 Agent 失败由 handler 抛错进入同一套重试逻辑。

## 30 秒演示脚本

1. `curl /api/platform/health` → 展示 `runtime`：3 次尝试、30s 超时、200ms 起退避、回滚开关。
2. 带 `PLATFORM_FAIL_NODE_IDS=report` 启动，运行主链路 → 监控页看到失败步骤「尝试 3 次」和错误堆栈，前 11 步完好。
3. 加 `PLATFORM_ROLLBACK_ON_FAILURE=true` 再跑 → 运行状态「已回滚」，输出显示回滚到 `revise-loop/verify-loop`、分数 0.86。
